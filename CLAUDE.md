# yt-dlp-clipper

A cross-platform (Linux/Windows/macOS) desktop app to pull videos with **yt-dlp**
and trim them **frame-accurately**, saving the full video, a clip, or audio-only.

## Build & run

System prerequisites (build-time):
- FFmpeg dev libraries: `libavcodec-dev libavformat-dev libavutil-dev libavfilter-dev libavdevice-dev libswscale-dev libswresample-dev`
- `clang` (for bindgen), `pkg-config`
- `libasound2-dev` (ALSA, for cpal audio)

Runtime: the `yt-dlp` binary, and an `ffmpeg` binary (yt-dlp uses it to merge video+audio).

```
cargo build            # debug
cargo test             # unit + integration tests (need ffmpeg + ffprobe)
cargo run              # launch the GUI
cargo run -- <path>    # launch and open a local video
```

## Architecture

- **lib (`src/lib.rs`)** — reusable, GUI-free modules:
  - `decoder` — frame-accurate decode/seek/step (seek to keyframe ≤ target, decode forward to exact frame). Timestamps in stream time-base; container-duration fallback for WebM. `Decoder::open` requires a video stream; `audio_duration_secs` is the audio-only counterpart, returning the timeline length for a source that has audio and no video (same stream-then-container duration fallback) and erroring when there's no audio either — which is what lets the decoder thread tell an audio-only file apart from a genuine decode failure.
  - `export` (`src/export/`) — split into `mod.rs` (public API `ExportSpec`/`Mode`/`VideoFormat`/`AudioFormat`, the `export_full`/`export_clip`/`export_audio_only` dispatch, `write_header`, `seek_to`), `plan.rs` (the copy-or-re-encode decision), `copy.rs` (stream-copy helpers + the paths that never decode), `video.rs`/`audio.rs` (the two re-encode pipelines), `transcode.rs` (the writer). Every export decides what to do with each stream **once**, in `StreamPlan::video_export`/`audio_export`, which reads the opened input and yields a `VideoPlan { reencode }` + `AudioPlan { encode_to: Option<Id> }`; `is_copy_only()` then picks the pure-remux short-circuit and `transcode` acts on that same plan, so the two can't disagree (they previously re-derived the predicates from two separate opens of the file). Per stream it **copies when the chosen container can hold the codec and re-encodes when it can't**, targeting the container's native codecs (H.264/AAC for MP4·MOV·MKV, VP9/Opus for WebM); `video_fits`/`audio_fits` + `container_kind` + `audio_encode_codec` decide. `ExportSpec.compatibility_mode` (on by default; GUI "Compatible" toggle by the Video format dropdown) narrows the MP4/MOV copy rules so a saved file plays on phones/TVs, not just computers: `video_fits` allows only H.264 (HEVC/AV1/MPEG-4 re-encode), `audio_fits` only AAC/MP3 (AC-3/ALAC re-encode), and `video_copyable`'s `pix_copy_safe` guard forces a re-encode of non-8-bit-4:2:0 H.264 (e.g. 10-bit/HDR). With it off, any codec/pixel format the container can hold is copied as-is. It doesn't affect MKV/WebM (inherently non-iOS) or audio-only exports. Full additionally short-circuits to a pure-copy `remux_copy` when every stream already fits — that path carries subtitle/data streams through too, since nothing there is decoded, whereas `transcode` maps only the planned video + audio. Clip always re-encodes video for a frame-accurate `in`, **and always re-encodes audio** so the cut is sample-accurate (a stream copy can't split a packet, so an exact `in`/`out` needs a re-encode); Full copies audio when it fits. AudioOnly re-encodes to MP3/AAC via `transcode` on a video-less plan (`windowed`, so `atrim` still cuts to the exact sample), or `Original` lossless stream-copy through `export_audio_copy` into a container that fits the source codec — that one stays separate because its window is packet-granular, since copies can't split a packet. Copied streams go through `add_copy_stream` (which resets the codec tag) and `write_packet`, the one place a packet is rescaled into an output stream's time base — read from the muxer each write, since `write_header` is what fixes it; x264 opened with a preset + `qmin/qmax/me_range/gop` unset so it accepts the settings. Clip video has a frame-count backstop so sources with missing frame PTS can't re-encode to EOF, and a clip keeps reading audio past the video's end so interleave lag can't truncate the tail. Audio re-encode (`AudioReenc`) runs `abuffer→atrim→abuffersink` (sink chunked to the encoder frame size); the `atrim` window is computed in samples from the first decoded frame's PTS, trimming the cut to the exact sample, and output PTS are stamped from a running sample counter to stay monotonic. That window is an `Option`: Clip and AudioOnly pass one, **Full passes `None`** and the graph substitutes `anull`, since Full re-encodes audio only because the container can't hold the source codec — passing the clip range there gave a full-length video a clip-length audio track (`full_keeps_whole_audio_when_the_codec_forces_a_reencode`). The GUI's Video/Audio format dropdowns (`VideoFormat`, `AudioFormat`) pick the output container. `ExportSpec.scale_height` optionally **downscales** the saved video (aspect-preserving, even dims via `scaled_dims`, never upscales); since a copy can't scale, a downscale forces the re-encode path (incl. routing Full away from `remux_copy`).
  - `ytdlp` — wraps the `yt-dlp` binary (fetch `-J` metadata, download with progress, size estimate). `available_heights` lists the source's distinct video heights (tallest first) and `resolution_selector` builds the `-f` expression (`bestvideo[height<=H]+bestaudio/…`) for the GUI's download Resolution menu; both cap at what the source offers.
  - `audio` — cpal output; decodes+resamples the audio stream on a worker thread; `clock_secs()` is the A/V **master clock**.
- **bin** — egui/eframe GUI under `src/app/` (see the `main.rs` restructure note for the full map). `app/mod.rs` holds `App` and the `eframe::App` impl; state in `app/*.rs` (`action`, `clip`, `playback`, `source`, `jobs`, `settings`, `ui_state`, `download`, `export_options`); panels in `app/ui/*.rs` (`toolbar`, `settings_window`, `error_panel`, `cache_window`, `preview`, `timeline`, `controls`, plus the shared `time_axis`). Layout: top toolbar (URL/fetch/open/from-cache/settings), central video preview (aspect-fit, fills width / full height for portrait), bottom clip controls (overview bar, timeline, transport, Start/End, save).
  - **Decoding runs on a background thread** (`DecoderHandle`): the UI sends seek/step requests (coalesced to the latest) and receives frames + metadata; it never blocks on a decode. Seeks are **generation-tagged** so superseded mid-drag decodes are dropped and the playhead pins to the released spot.
  - **Audio-only sources** (a `bestaudio` download, or the Audio checkbox without Video) open as `DecodeEvent::OpenedAudioOnly`, setting `DecoderHandle::has_video` false. They get a real timeline and a working "Save audio only"; only the two video saves are disabled, and the preview says so instead of showing the open-a-file prompt. Since no frame ever arrives to carry the position, `move_audio_only_playhead` sets `current_secs` directly for a scrub or skip (stopping playback so the audio clock can't overwrite the new spot), playback advances the playhead straight off the master clock, and frame-stepping is inert. Reporting these as a decode error instead is what made the app unable to save them at all.
  - **One worker at a time** — `Jobs::spawn` puts a fresh `Receiver` in its private `rx`, so a second call while a job runs would drop the first receiver and strand a thread that keeps working with nowhere to report (every `tx.send` is discarded). `Jobs::is_worker_busy()` gates Fetch, Download, and the three Save buttons so a second job can't be started. Settings actions (`yt-dlp -U`, the update check) hold **their own** channels instead, since neither should wait on a download.
  - **Playback**: video chases the master clock (audio if available, else wall time).
  - **Timeline zoom** — `view_start_secs`/`view_end_secs` are the span `timeline::timeline` maps across its rect (not the whole duration), for frame-level work on long videos. `timeline::overview_bar` above it always shows the *whole* video with the clip region tinted and the zoom window outlined; a drag there resolves to a `WindowDrag` by where the press landed — `Start`/`End` within `HANDLE_GRAB_RADIUS` of an edge, `Pan` inside the window, else `Draw` (sweep a new window, which is also what a window already spanning the whole video gets, having nowhere to pan). Scrolling over the timeline zooms about the cursor and clamps out to the full duration. **Zoom is view-only** — it never moves the clip in/out points, so they can sit outside the window, and the timeline neither paints nor grabs a marker that does. The timeline's own in/out markers are draggable, clamped `MIN_RANGE_SECS` apart by `clamped_in_secs`/`clamped_out_secs`. `set_view` floors the span and keeps the window inside `[0, dur]`; both bars go through `TimeAxis`, which floors the width at `f32::EPSILON`, since a `0.0 / 0.0` from a collapsed panel would put a NaN into the view bounds that no later clamp clears.
  - **Gesture-scoped undo** — a continuous drag is one undo step, not one per frame: `begin_gesture` stashes the pre-gesture `ClipRange` in `pending_undo_range`, the drag mutates freely, and `commit_gesture` on release pushes it only if the state actually changed (so a round-trip drag records nothing and leaves `redo_stack` intact). Scroll-zoom has no release, so `scroll_gesture_commit_at` closes it after `SCROLL_GESTURE_IDLE_SECS` idle. `commit_abandoned_gesture` runs at the **end** of `update()` — after the panels have drawn, so it can't clear a normal release before the bars apply the drag's final position — and recovers state a missing `drag_stopped` would strand.
  - **Keyboard shortcuts** (`Keybinds`/`Bind`): set-start (S), set-end (E), play/pause (Space), undo (Ctrl+Z), redo (Ctrl+Y) by default, all **rebindable** in Settings (click the action, press a new key; Esc cancels; `rebind` swaps to keep keys distinct). A `Shortcut` is a key plus required Ctrl/Shift state; persisted by key *name* + those modifier flags (so it doesn't need egui's serde feature; the loader falls back to the older ctrl-less format). Undo/redo operate on a `ClipRange` snapshot of the clip in/out timestamps **and** the zoom window: `set_in_secs`/`set_out_secs` push one onto `undo_stack` (capped at `CLIP_HISTORY_LIMIT`, clearing `redo_stack`) before each edit, and history clears on a new video. The Set Start/End buttons show their key; the main shortcut handler is suppressed while a text field has focus (so Ctrl+Z is text undo there) or Settings is capturing a key.
  - Settings persist via eframe storage through `Settings::load`/`save` (one key per field; format frozen so an older build still reads it). Downloads go to a managed cache dir (`eframe::storage_dir("yt-dlp-clipper")/downloads`).
  - **Button icons** are SVGs in `assets/` (`save.svg`, `download.svg`, `settings.svg`), embedded via `egui::include_image!` and rasterized by `egui_extras` (svg feature, resvg) after `install_image_loaders` at startup; `icon_button()` builds an icon+text button, sizing the icon to the button font height so it lines up with the caption. Unicode glyphs render as missing-glyph boxes in egui's bundled fonts, hence SVGs.

## Conventions

- **No magic numbers** — hoist literals to named `const`s, or use a library constant (e.g. `ffmpeg::ffi::AV_TIME_BASE`).
- **Default to no comment** — code should read and be understood on its own. Make it self-documenting with explicit, descriptive names (variables, functions, consts) rather than a comment explaining a vague one. Add a comment only when the code encodes a non-obvious invariant a reader can't infer; if unsure, leave it out.
- **Comments explain why, never what** — the code already shows what it does; a comment repeating that is noise. Write one only for a fact the code can't carry on its own: a non-obvious invariant, an external constraint, a cited reason. Never explain why something *wasn't* done (no narrating rejected alternatives); drop dead code instead of commenting around it.
- **No narrative comments** — a comment must stand on its own to a reader with zero history of how the code came to be. Don't narrate the development process or refer to it: no "the collapse happens a frame before the menu opens", no "we tried X but", no temporal/conversational framing ("now", "still", "previously", "as noted above"). State the rule the code follows and the invariant it relies on, in the present tense, as if the code had always been this way. E.g. prefer "A pointer press collapses the selection; restore it so the menu acts on it" over "egui clobbers the selection on press a frame before the menu opens, so grab it first".
- **Avoid adding a crate for one small thing** — prefer std or an existing dep (e.g. `eframe::storage_dir` instead of `dirs`). New deps are fine for genuine core needs (cpal for audio, ffmpeg-the-third).
- **Don't assume a glyph renders** — egui's bundled fonts lack many Unicode symbols (`⟦⟧`, `→`, and others), which show as missing-glyph boxes in the UI. For those, use an SVG icon in `assets/` (embedded via `egui::include_image!`) instead of the character. **Tint every icon to the theme's text color** (`.tint(ui.visuals().text_color())`, dimming to `weak_text_color()` when disabled) rather than hard-coding a fill, so it stays legible in both light and dark themes.
- **The tree is hand-formatted — never run `cargo fmt`.** It would rewrite files wholesale (`main.rs` alone churns ~1100 lines) and bury a real change. Keep lines within 100 columns by hand.
- **`cargo clippy` is not clean**, and its `map_or` → `is_none_or` suggestion is declined throughout: `is_none_or` needs Rust 1.82, the crate pins no `rust-version`, and CI's toolchain floor is unverified. Match the surrounding `map_or`.
- This machine has no usable `sudo`; system packages must be installed by the user.

## Planned / TODO

### `main.rs` restructure (done)
`App` is split into eight sub-structs, each in its own module, every panel is a free function taking only the state it touches, and the whole GUI lives under `src/app/`.

**Layout** — `main.rs` is 72 lines: `main()`, `self_test()`, the top-level `mod` declarations, and the tool-binary resolution, plus `STORAGE_APP_ID`/`APP_DISPLAY_NAME`/`SELF_TEST_FLAG`. `App::new(cc, cli_path)` owns the startup wiring (load settings, apply zoom + theme, open a CLI path), so every `App` field stays private.
- `app/mod.rs` — `struct App` + `Default`, the `eframe::App` impl, `SKIP_SECS`/`AUDIO_ONLY_FPS`/`NAV_REPEAT_*`, and the coordinating methods that genuinely span concerns: `new`, `poll`, `poll_decoder`, `reset_for_new_video`, `load_video`, `start_export`, `apply`, `apply_nav`, and the transport helpers `skip_secs`/`step_frame`/`toggle_play`/`toggle_play_clip`/`play_from`/`move_audio_only_playhead`/`start_playback`.
- `app/*.rs` — state: `action.rs`, `clip.rs`, `playback.rs`, `source.rs`, `jobs.rs`, `settings.rs`, `ui_state.rs`, `download.rs`, `export_options.rs`.
- `app/ui/*.rs` — panels: `toolbar.rs`, `settings_window.rs`, `error_panel.rs`, `cache_window.rs`, `preview.rs`, `timeline.rs`, `controls.rs`, plus the shared `time_axis.rs`. `app/ui/mod.rs` holds `CONTROL_PAD` and `INPUT_MARGIN`.
- Outside `app/`: `binaries.rs`, `cache.rs`, `decoder_thread.rs`, `format.rs`, `keybinds.rs`, `theme.rs`, `widgets.rs` — none of them touch `App`.

**`App` fields** — `download`, `jobs`, `source`, `clip`, `settings`, `ui`, `export_options`, `playback`. No loose fields.

**Verification (still the recipe for GUI changes)** — `cargo build` must finish with **zero** warnings (unused imports pile up fast when a function moves out). `cargo test` is 54 tests over 5 binaries, 1 ignored (`queries_the_live_release_feed`, which reaches the real GitHub endpoint under `--ignored`). Those cover the **lib only**: the GUI under `src/app/` has zero test coverage, so also launch the GUI — `timeout 10 cargo run` should be killed at the timeout (exit 124) with nothing on stderr. That proves startup and one clean frame; it does **not** exercise the timeline gestures (undo/redo, scroll-zoom, marker drags), which still need a human. Keep every line within 100 columns by hand; `awk 'length>100' src/*.rs src/app/*.rs src/app/ui/*.rs` should show nothing outside `widgets.rs`.

**Design decisions worth keeping**
- **A cluster's methods move with it only when they touch nothing else.** `Clip` took all 15 of its methods; `Playback` took only `stop`/`start`/`master_clock`, because the transport helpers coordinate decoder + clip + settings and would only have gained parameters by moving. Those stay on `App` as the sequencing layer.
- **Moving a panel to a file is not the point — narrowing its borrow is.** A panel still taking `&mut self` keeps its copy-out/write-back block. `settings_window` is the proof: as a free `show(ctx, &mut Settings, &mut UiState, &mut Jobs)` it edits fields directly, because `egui::Window::open` takes `&mut ui_state.is_settings_open` while the closure captures `ui_state.pending_scale`/`rebinding` separately — edition 2021's disjoint closure captures. Its prologue of locals and its write-back block are gone, and its six deferred flags are down to one: `apply_scale`, kept because retuning the zoom factor mid-window would apply a new scale to a half-drawn frame. The theme is applied after the window for the same reason.
- **Panels report, `App` acts.** Every panel does inline whatever its own borrow covers (Pause, volume, the seek's `playback.stop()`, the output-folder picker) and reports the rest as an `Action` (`app/action.rs`): `Fetch`, `OpenFile`, `Nav`, `TogglePlay`, `PlaySelection`, `Export`. `update()` collects them into one `Vec<Action>` in panel-draw order and drains it through `App::apply` after every panel has drawn, so nothing mutates state a widget still holds. `clip_controls` takes `&mut Vec<Action>` (it can emit a seek and a transport action in one frame); the others return `Option<Action>`.
- **`Nav` stays its own enum inside `Action::Nav`.** `Nav` means "send this to the decoder", and `apply_nav`'s `!has_video()` arm — which drops steps and moves the playhead directly for an audio-only source — would be wrong if `TogglePlay`/`PlaySelection` rode along in it.
- **`Fetch` carries its own reset.** The `Action::Fetch` arm runs `reset_for_new_video` (which clears the worker receiver) and *then* `Jobs::spawn`, both in the one place. Split across the panel and the drain, the deferred half would clear the receiver the other half just installed. The drain costs one frame of latency on Fetch and Open: the outgoing video's panels draw once more before the reset lands.
- `Clip` holds the in/out points, the zoom window, both drag states, and the undo/redo stacks, with `ClipRange`/`WindowDrag`/`TimelineDrag`/`MIN_RANGE_SECS`/`CLIP_HISTORY_LIMIT` alongside. Methods dropped the redundant `clip_` prefix (`clip_range`→`range`, `undo_clip_edit`→`undo`, `clear_clip_history`→`clear_history`). `Playback` holds the clock origin, `play_until`, the `AudioPlayer`, and `awaiting_release` — the last one lives here so `stop()` clears it where the rest of the playback invariant is maintained. Folding `toggle_play`'s and `play_from`'s identical eight-line tails into `Playback::start` removed that duplication.
- `Jobs` holds background work and what it reported: the shared worker channel, `status`/`saved_path`/`last_error`, download progress, the export flags, both cancel flags, and — deliberately together — the yt-dlp and app-update channels, since those write the same `status`/`last_error` surface. `rx` is **private**, reached through `spawn`/`is_worker_busy`/`take_receiver`/`restore_receiver`/`clear_receiver`, so the one-worker-at-a-time rule can't be broken by an outside assignment. `Msg` and `UpdateState` moved with it. `poll` stays on `App` (it calls `load_video` and reads `settings.open_dir_on_save`) but reports through `succeed`/`finish_export`. **`ExportCanceled` must not use `succeed`** — it leaves `last_error` intact on purpose, so a cancel never swallows a prior failure.
- `Source` holds the decoder handle, origin path, export title, and preview texture, plus `OpenedSource`. Its boundary is the **open file**, not the fetch: `url`/`info` live on `Download` because they follow the yt-dlp fetch lifecycle, which is why `reset_for_new_video` clears the four decoder fields but leaves those two. `is_ready`/`has_video`/`ready_position_secs` replace four hand-rolled `decoder.as_ref().is_some_and(|d| d.ready)`-style chains.
- `Settings` holds the nine persisted fields plus `load`/`save`/`effective_download_dir`. The `*_KEY` consts are private to `app/settings.rs` and named in exactly two places. **The on-disk format is unchanged** — one key per field, same names and types — so existing installs keep their settings, and a Phase 3 self-update rollback to an older build reads the same keys. A single serde-struct key was considered and rejected for that reason. `pending_scale`/`is_settings_open`/`rebinding` are **not** persisted; they live on `UiState`.
- The UI-state type is **`UiState`, not `Ui`** — a type named `Ui` beside the hundreds of `ui: &mut egui::Ui` parameters reads as a trap. It nests `CacheBrowser`, whose `rx` is private behind `open`/`poll`/`close`. `Download` and `ExportOptions` carry no methods; they group fields so a panel can take `&mut Download` instead of `&mut self`.
- **`TimeAxis` (`src/app/ui/time_axis.rs`)** — both timeline bars previously built their own `x_at`/`t_at` closures with the `width.max(f32::EPSILON)` NaN guard and their own two-handle `HANDLE_GRAB_RADIUS` hit-test. `TimeAxis::new(rect, start_secs, end_secs)` owns `x_at`/`secs_at`/`fraction_at`/`contains`, so the guard against a collapsed panel exists once; the free `nearest_handle(x, [(Option<f32>, T); 2])` serves both, `None` meaning a handle scrolled outside the visible span and therefore ungrabbable. The overview passes `0..dur`, the timeline `view_start..view_start + span` — the caller floors that span at `MIN_RANGE_SECS`, which `TimeAxis` must not lower to its own `f64::EPSILON`.

### Pin `rust-version`, then migrate to edition 2024 (not built)
Two changes, in that order. The first is worth doing on its own; the second depends on it.

- **Pin the toolchain floor first.** `Cargo.toml` declares no `rust-version`, and what the CI runners actually install is unverified, so every "can we use this?" question gets answered by guessing. That is already why `is_none_or` (Rust 1.82) is declined throughout in favour of `map_or`. Add a `rust-version` key and confirm the three release jobs (AppImage on `ubuntu-22.04`, vcpkg/MSVC on `windows-latest`, `macos-14`) agree with it. Once the floor is known, the `map_or` workaround can be revisited independently of the edition.
- **Then edition 2024** (needs Rust 1.85; **let-chains need 1.88**). The payoff for this codebase is let-chains: `if let Some(dec) = &self.source.decoder { if dec.ready { … } }` collapses to one condition, and `timeline`, `poll_decoder`, and the transport controls are all built from that shape. Edition 2024 adds **nothing** for closure captures — the disjoint-capture rule that lets `settings_window` borrow `ui_state.is_settings_open` and `ui_state.pending_scale` at once is already edition 2021.
- **Risks** — `if let` temporary scope changes in 2024 (scrutinee temporaries drop before the `else` block instead of after); this tree is lower-risk than most, holding no lock guards across those branches, but it is a real behaviour change rather than a rename. `cargo fix --edition` does the mechanical work; **check its output for hand-formatting churn**, since `cargo fmt` must never run here.
- **Order relative to the restructure** — after, not during. The restructure's slices are verified by running an app with no test coverage, and an edition bump changing behaviour underneath that would confuse which change broke what.

### Frame-step forward optimization (not built)
`decoder::step_by`'s forward branch loops `step_forward()` for a net-positive step count, and each call runs `to_image()` to build a full `egui::ColorImage` that's then discarded for all but the last frame. Not a leak (intermediates are freed) and `n` is usually 1–2, but for a large net-forward jump it's wasted decode→convert churn. Optimization: decode *through* the intermediate frames without converting (only `to_image` the final one). Low priority.

### yt-dlp bundling + in-app update (mostly built)
yt-dlp breaks often as sites change, so it must be kept current.
- **Binary resolution + seeding (built)** — `resolve_ytdlp()`/`resolve_ffmpeg()`/`find_in_path()` in `main.rs` resolve to **absolute paths** (managed copy → next-to-exe (bundled) → PATH) at startup and pass them to `ytdlp::set_binary`/`set_ffmpeg` (global `OnceLock<PathBuf>`); every invocation uses the full path, never the bare name. yt-dlp is **seeded into a writable managed dir** (`storage_dir/bin/`, `0755`) so `yt-dlp -U` works even when installed read-only (`.app`/AppImage/`Program Files`). ffmpeg isn't seeded (never self-updates).
- **Security hardening (built)** — the managed `bin/` is owner-only-writable (`set_owner_only`, 0755 on unix; no-op on Windows ACLs) so a local user can't swap the binary we run; download passes **`--ffmpeg-location <resolved ffmpeg>`** (verified in `tests/ffmpeg_location.rs`) so yt-dlp merges with our exact ffmpeg and never searches PATH/CWD for a planted one.
- **Update UI (built)** — `ytdlp::version()`/`update()` (`yt-dlp -U` on a worker → `Msg::YtdlpUpdated`); `ytdlp_version`/`ytdlp_updating` on `App`. Settings shows the version + an Update button; failures surface full text via the **error panel** (`error_panel`, `last_error`), which also shows an **Update yt-dlp** button when `ytdlp::suggests_update` matches yt-dlp's outdated-binary hints. Detecting "newer exists" before updating would need a GitHub HTTP check, so `-U` itself is the check (no-op when current); **App self-update** adds an HTTP client that could revisit this.
- **QuickJS runtime bundling (built)** — YouTube's cookie-honoring `web` client needs an external JS runtime to solve its nsig/PO-token challenge, or age-restricted fetches fail with a terminal error instead of the recoverable one `suggests_cookies` handles. `resolve_qjs()` bundles [quickjs-ng](https://github.com/quickjs-ng/quickjs)'s `qjs` (~1–2.5MB vs. deno's ~90–190MB) the same way as `ffmpeg`, and `ytdlp::set_js_runtime` passes it as `--js-runtimes quickjs:<path>` — additive, not a replacement for a `deno` already on PATH. Tests split across `tests/js_runtime_{fetch,download}.rs` since `QJS_BIN` is a process-global `OnceLock`.
- **Remaining** — actually ship the `yt-dlp`/`ffmpeg` binaries in the package so resolution finds a next-to-exe copy (today it falls through to PATH); verify the read-only-bundle → managed-copy path on real `.app`/AppImage builds; the managed ffmpeg copy never refreshes when the app updates (see **App self-update** Phase 0).

### App self-update (not built)
The app ships outside any store and yt-dlp breaks on a timescale of weeks, so a build that can't update itself quietly stops working. Updates come from the GitHub Releases API (`/repos/0xTheCrow/yt-dlp-clipper/releases/latest` — `tag_name` + `assets[].browser_download_url`, parsed with the `serde_json` already in the tree), so there is no server to run. Requests need a `User-Agent` (GitHub 403s without one); the unauthenticated limit of 60/hour per IP is far above one check per day, and `/latest` already excludes drafts and prereleases so a half-uploaded release is never offered.

- **Dependency** — `ureq` 3.4 (blocking, rustls, no tokio), 14 crates. `ring` compiles clean for `x86_64-pc-windows-msvc` under `-C target-feature=+crt-static`, checked with `cargo xwin build -p ureq --target x86_64-pc-windows-msvc`; the whole app can't be Windows-checked off CI, since `ffmpeg-sys-the-third` needs the vcpkg FFmpeg, so a CI run remains the final word. ureq's `native-tls` feature is the fallback if it ever does fight.
- **Phase 0: managed ffmpeg freshness (built)** — `embedded_ffmpeg_cli` gates the managed copy on a `.ffmpeg-version` stamp holding `env!("CARGO_PKG_VERSION")`, written only after a successful extraction, so a `bundle-tools` build shipping a newer ffmpeg replaces the copy an earlier build extracted rather than keeping it forever. Only `bundle-tools` builds are affected: the AppImage and `.app` stage ffmpeg inside the bundle, where `resolve_ffmpeg`'s bundled-first order picks up a replacement for free. yt-dlp is deliberately not stamped — re-extracting it would downgrade a copy `yt-dlp -U` has since updated. Settings carries a **Bundled tools → Reset** over `reset_bundled_tools()`, which reports that a restart is needed because the resolved paths live in a `OnceLock` for the process lifetime.
- **Phase 1: check only (built)** — `updater::check()` in the **lib** queries the release feed and yields `Some(AvailableRelease { version, notes, page_url })` only when the tag parses above `env!("CARGO_PKG_VERSION")`. `parse_version` compares a `major.minor.patch` tuple (no semver crate), tolerating a `v` prefix, absent components, and prerelease/build suffixes. The check runs on **its own channel** (`update_rx`) rather than `App::spawn`, which replaces `rx` and would orphan a download or export already reporting on it. Settings shows the app version, a **Check for updates** button (deferred `start_*` flag, so nothing mutates `self` mid-closure), and the outcome; an available release links to its GitHub page, nothing having a downloader until Phase 3. `main` scans argv for `--self-test`, which runs `ffmpeg::init()` and exits 0 without a GUI. Tests sit inline in `updater.rs` (matching `ytdlp.rs`) over parsing, ordering, and selection; `queries_the_live_release_feed` is `#[ignore]`d and reaches the real endpoint under `cargo test -- --ignored`.
  - Asset selection (`platform_asset_suffix`) is deliberately absent: its only consumer is the Phase 3 downloader, and the macOS `.zip` it would name arrives in Phase 2. The auto-check toggle belongs to Phase 4, since a persisted checkbox governing nothing would misrepresent the app. `--finish-update` lands with the macOS helper in Phase 3.
- **Phase 2: signing** — TLS proves the bytes came from GitHub; a signature is what survives a compromised release or a rogue CA. ed25519 keypair, private half a CI secret, public half a `const` in `updater.rs`. CI signs each asset with `openssl pkeyutl -sign -rawin` (already on every runner, no new tooling) and uploads `<asset>.sig`; the app verifies with `ed25519-dalek` before anything touches the install location. macOS must also publish a **`.zip` of `Cooper Clipper.app`** — a `.dmg` is a distribution container, awkward as an update payload.
- **Phase 3: stage + apply** — download to `storage_dir/updates/<version>/`, verify, then swap. `Msg::UpdateProgress` stays separate from `Msg::Progress`, which drives the yt-dlp download bar. Linux/Windows/macOS ship together, not staged one-platform-at-a-time; Windows/macOS swap logic is unverified until run on real hardware, the same caveat already accepted for the QuickJS packaging bundling.
  - **Linux** — copy the running AppImage to `storage_dir/backup/` (it may sit on a different mount than `$APPIMAGE`, which rules out a hardlink), then `rename()` the payload over `$APPIMAGE`: POSIX-atomic, and the running process keeps its inode. `make-appimage.sh` should drop the version from `OUTPUT`, else an in-place replace leaves a filename that lies.
  - **Windows** — rename `app.exe` → `app.exe.old`, write the payload to `app.exe`, relaunch. Windows permits renaming a running exe but not deleting it; this is the mechanism `yt-dlp -U` already uses.
  - **macOS** — the target is a directory, so a `/bin/sh` helper in temp waits on the pid and swaps. A copy of the bare Mach-O can't serve as the helper: `dylibbundler` rewrote its install names to `@executable_path/../libs`. Unzip to staging **before** touching the target so the window where no app exists is a single `mv`, and restore the backup on every failure branch.
  - **Restart gate** — `self.rx.is_some()` means a worker is running. Idle offers **Restart now**; busy holds at `ReadyToApply` and applies at next launch, so an export is never interrupted.
- **Phase 3 rollback — the old build survives until the new one proves itself.** Two independent defenses:
  - **Pre-swap probe** catches "won't start at all": run the staged payload with `--self-test`, require exit 0 within a timeout, treat a hang as failure. It runs on the user's actual machine, so it catches the AppImage's glibc floor, a wrong-arch asset, and a corrupt download *before* the working install is gone. Signal on **exit code, not stdout** — adding `windows_subsystem = "windows"` later would silently break a stdout probe.
  - **Commit protocol** catches "starts, but is broken": `storage_dir/update-state.json` (`target`, `backup`, `staged`, `from_version`, `to_version`, `launch_attempts`) written before the swap. On startup, when `to_version` matches the running build, increment `launch_attempts` and **flush before any risky init** so a hard crash still counts; delete backup, staged payload, and state file at the end of the first successful `App::update()` frame. At `launch_attempts >= UPDATE_LAUNCH_ATTEMPT_LIMIT` (2), restore the backup and relaunch. A mismatched `to_version` means the swap never took — clean up.
  - Keep the staged payload until commit so a rollback retries without re-downloading. Peak client-side disk is ~3× the bundle (~423 MB against the 141 MB AppImage), freed at commit; check free space before staging.
  - Residual risk: a build that passes the probe then wedges before the attempt increment never auto-rolls-back. The backup stays at a known path — runnable directly on Linux, `app.exe.old` on Windows — which belongs in the README rather than in more machinery.
- **Phase 4: auto-check** — on startup when enabled and `now - last_check > UPDATE_CHECK_INTERVAL_SECS`. Failures are silent (a dead network must never raise the error panel at launch) and `last_check` is written whatever the outcome, so a persistent failure doesn't retry every boot. A dismissible banner near `error_panel` offers Update / Later.
- **Verification** — pure logic unit-tests in `tests/updater.rs`: version parse and ordering (`0.1.10 > 0.1.9`), asset selection from a captured API response, signature valid/flipped-byte/truncated, and a release with no matching platform asset erroring rather than panicking. The swap needs a manual matrix against a deliberately broken 0.1.5 — probe failure (truncated binary, install left untouched), immediate-exit build (rolls back on the second launch), update during an export (deferred), kill mid-download (next launch clean), settings surviving a rollback. Confirm macOS gains **no new quarantine prompt**: fetching the payload ourselves doesn't stamp `com.apple.quarantine`, which is the main UX win over a manual download.
- **Order** — 0 → 1 → 2 → 3 → 4. Phases 0 and 1 are independently shippable; 1 and 2 both land before 3, since 3 is the first phase that writes to the install location.

### Clip/Full audio for non-MP4 codecs (solved)
Previously "Save clip" stream-copied audio into MP4, so an **Opus** source (common in
large YouTube downloads) produced `track 1: codec frame size is not set` and a
malformed audio track. Now `transcode()` re-encodes any stream the chosen container
can't hold (Opus→AAC, VP9/AV1→H.264) and copies the rest, so MP4/MOV/MKV all produce
valid files from any source. Covered by `clip_transcodes_opus_audio_into_mp4` and
`full_transcodes_vp9_into_mp4` in `tests/export.rs`.

### Packaging (for distribution)
- **CI is wired** in `.github/workflows/release.yml`: a `v*` tag builds all three bundles and publishes a GitHub release with them attached; `workflow_dispatch` builds them on demand and leaves them in the run's Artifacts (no release). Linux, Windows, and macOS each run on their own native runner (`ubuntu-22.04`, `windows-latest`, `macos-14`). All runners are free for this public repo (no minute cap).
- **Static FFmpeg is wired** as the off-by-default `static-ffmpeg` cargo feature (see `Cargo.toml`): it enables `ffmpeg-the-third`'s `build` + `build-lib-{x264,vpx,opus,mp3lame}` + `build-license-gpl`. x264 (no native H.264 encoder exists) makes the binary **GPL** — accepted. Default builds stay dynamic so the no-sudo dev box keeps working; the static build is for CI and **requires `nasm`/`yasm` plus STATIC libx264/libvpx/libopus/libmp3lame** (FFmpeg's configure links them; `build` does not vendor them) and git-clones FFmpeg at build time. Build: `cargo build --release --features static-ffmpeg`.
- Static libav* removes the app's own FFmpeg dependency, but yt-dlp still needs an `ffmpeg` **CLI** at runtime to merge — bundle that binary too (see below).
- The **`bundle-tools`** cargo feature embeds `yt-dlp` and the `ffmpeg` CLI binary into the exe at compile time and extracts them to a per-user managed dir on first run. Used by the Windows CI job to produce a single `.exe`. It enables `ffmpeg-the-third/static` (link libav* statically) but does **not** imply `static-ffmpeg` — `static-ffmpeg` runs `./configure` via the Rust build script, which works on Linux/macOS but fails on Windows (the build script runs as a Windows process that can't exec shell scripts). Instead, the CI pre-builds FFmpeg 6.0 statically in an MSYS2 shell (where configure works), then sets `FFMPEG_DIR` and `CODEC_LIB_DIR` for the Rust build. Requires `BUNDLE_YTDLP`, `BUNDLE_FFMPEG_CLI`, `FFMPEG_DIR`, and `CODEC_LIB_DIR` at build time.
- Packaging is hand-rolled per-target scripts (`scripts/make-{appimage,windows,macos}.sh`) rather than `cargo-dist` → AppImage (Linux), single `.exe` (Windows), `.dmg` (macOS). **No code signing/notarization** (distributing to friends; users will see Gatekeeper/SmartScreen warnings).

#### Linux AppImage (built)
`scripts/make-appimage.sh` produces a single self-contained `yt-dlp-clipper-<ver>-x86_64.AppImage`. It does **not** need the `static-ffmpeg` feature: it builds the normal **dynamic** release, then `linuxdeploy` bundles the app's `libav*`/`libasound` deps into the bundle (`RUNPATH=$ORIGIN/../lib`). It downloads and bundles a **static ffmpeg** (BtbN, GitHub-hosted — johnvansickle 415s the CI runner) and the self-contained **`yt-dlp_linux`** (the PyInstaller build — *not* the local python zipapp, which needs python3) into `usr/bin/` next to the exe, where the resolver finds them. Inputs: `packaging/yt-dlp-clipper.desktop` + `assets/yt-dlp-clipper.png`.
- **No sudo to build** — `APPIMAGE_EXTRACT_AND_RUN=1` avoids FUSE for the tooling. `libfuse2` is only needed so the *output* AppImage runs on a double-click (else `--appimage-extract-and-run`).
- Caveats: glibc is **not** bundled, so the AppImage runs on systems with glibc ≥ the build box's (build in an older container for wider reach); `libGL`/`libEGL` are `dlopen`ed and intentionally not bundled (present on every desktop).

#### Windows single exe (built natively on Windows in CI with MSVC + vcpkg)
The CI (`windows-2022` runner) builds a single self-contained `yt-dlp-clipper-<ver>-win64.exe`; whole binary is GPL (x264). The `bundle-tools` feature bakes `yt-dlp.exe` and a static `ffmpeg.exe` CLI (gyan `full_build`, no DLL deps) into the binary at compile time; static libav* links mean no DLL deps from the app either. The result is a truly standalone exe. First run extracts the embedded tool binaries to the per-user managed dir (`storage_dir/bin/`), where they persist and can be updated by `yt-dlp -U`.
- **CI build**: static FFmpeg + codecs come from **vcpkg** (`ffmpeg[avcodec,avformat,avfilter,swscale,swresample,gpl,x264,vpx,dav1d,opus,mp3lame]:x64-windows-static`, cached via `VCPKG_DEFAULT_BINARY_CACHE`). `dav1d` is the software **AV1 decoder** — without it the only AV1 decoder is FFmpeg's native HW-only one, which can't software-decode YouTube's AV1 streams and spams "Missing Sequence Header". `ffmpeg-sys-the-third`'s **vcpkg path** (`vcpkg::find_package("ffmpeg")`, selected because no `FFMPEG_DIR` is set and the target is MSVC) links libav* + the codec deps and, for static builds, **emits the Windows system libs itself** (`ole32`, `secur32`, `ws2_32`, `bcrypt`, `user32`) — so `build.rs` needs nothing Windows-specific (it only embeds the tool binaries). `VCPKGRS_TRIPLET=x64-windows-static` points the vcpkg crate at the static triplet; `-C target-feature=+crt-static` links the CRT statically (matching the triplet) so the exe needs no VCRedist. `LIBCLANG_PATH` points at the runner's LLVM for `ffmpeg-sys-the-third`'s bindgen pass. The app also drops the default `device`/avdevice ffmpeg-the-third feature (nothing opens a capture device).
- **Why MSVC + vcpkg, not MinGW cross-compile**: the prior approach cross-compiled a hand-built static FFmpeg from Linux with MinGW, which hit GNU `ld` single-pass link-ordering, Ubuntu-mingw `_FORTIFY_SOURCE`/`libssp`, and a hand-maintained transitive-dep list — all toolchain artifacts, not app problems. MSVC's linker resolves order-independently, has none of the fortify/libssp issues, and vcpkg supplies static FFmpeg with correct dependency metadata, so the whole class of failures disappears.
- `scripts/make-windows.sh` — **cross-compiles from Linux** (dev convenience, produces a zip bundle, not a single exe) for `x86_64-pc-windows-msvc` via `cargo-xwin`. Uses gyan 6.0 shared build DLLs. Prereqs: `rustup target add x86_64-pc-windows-msvc`, `cargo install cargo-xwin`, and (sudo) `lld llvm clang p7zip-full zip`.

#### Windows CI cache reliability (not built)
The Windows job's `VCPKG_DEFAULT_BINARY_CACHE` is backed by `actions/cache`, whose entries are evicted after 7 days unused. Releases can be months apart, so the cache is reliably cold on release day and every Windows build re-runs the full `vcpkg install` from source (x264 + libvpx + opus + mp3lame + FFmpeg itself, ~25 min) instead of the fast path the setup was meant to give — confirmed from a real run's log where every restore step reported a miss and the job took ~30 min end to end. A scheduled cache-warming cron job was considered and rejected (adds permanent recurring CI machinery to work around a caching layer that's the wrong tool for this access pattern). Candidates to explore instead:
- **Switch the vcpkg binary-cache backend from `actions/cache` to GitHub Packages (NuGet)** — vcpkg supports pluggable backends (`x-gha`, NuGet, Azure, S3, HTTP); a NuGet feed on GitHub Packages has no idle-time eviction, unlike the Actions cache. Likely the most direct fix since it targets the actual cause (wrong backend for this access pattern) rather than working around its lifetime.
- **Prebuilt FFmpeg artifact as a durable release asset** — build the static vcpkg FFmpeg package once (manually or on a vcpkg.json-change trigger) and publish it like the Linux job already does for BtbN ffmpeg; the Windows job downloads and extracts instead of running `vcpkg install`. Needs new build/publish/versioning tooling.
- Self-hosted runner (persistent disk, no cache needed at all) was ruled out: untrusted-code exposure isn't worth it on a public repo.

#### macOS .dmg (built — must run on a Mac)
`scripts/make-macos.sh` produces a self-contained `Cooper Clipper.app` and a `yt-dlp-clipper-<ver>-macos-<arch>.dmg` for the **host arch** (arm64 or x86_64 — no universal binary; the CI matrix covers both). It can't be cross-compiled from Linux the way Windows is: Apple's SDK isn't freely redistributable (so there's no cargo-xwin equivalent), and `cpal` links CoreAudio from that SDK. Like the AppImage, it builds the normal **dynamic** release and uses **`dylibbundler`** (the macOS counterpart to `linuxdeploy`) to copy the app's `libav*` dylibs into `Contents/libs` and rewrite their install names to `@executable_path/../libs`. A static `ffmpeg` CLI (osxexperts) + the self-contained `yt-dlp_macos` are staged in `Contents/MacOS/` next to the exe, where the resolver finds them. The `.icns` is generated from `assets/yt-dlp-clipper.png` (`sips`+`iconutil`); a minimal `Info.plist` is emitted inline.
- **Build against `ffmpeg@6`**, not brew's default 7.x (same 6.0 pin reason as Windows): the script sets `PKG_CONFIG_PATH` to `brew --prefix ffmpeg@6`. Prereqs (no sudo, just brew): `brew install ffmpeg@6 pkg-config dylibbundler` + Xcode command-line tools.
- **Unsigned/unnotarized**, so first launch needs right-click → Open (or `xattr -dr com.apple.quarantine` the `.app`).
